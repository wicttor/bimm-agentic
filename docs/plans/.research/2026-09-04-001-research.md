# Research Findings

## Patterns Found

Search was run against the stack detected in Step 1 (Node.js/TypeScript, Vite, React 19;
queries: `apollo`, `graphql`, `useQuery`, `mui`, `vitest`, `MockedProvider`, `msw`, `handler`).
**4 unique local pattern files** found -> confidence **HIGH** for the *generated-app* surface.

> Important asymmetry discovered: patterns are HIGH-confidence for what the agent must
> **produce**, and **zero** for what the agent must **be**. There is no LLM call, no agent
> loop, and no CLI entry point anywhere in the repo. The runtime is net-new code; only its
> output has local precedent.

- `src/components/Example.tsx` — **Apollo + MUI component pattern** (HIGH). `useQuery<{ cars: Car[] }>(GET_CARS)`
  with early-return `CircularProgress` (loading) and `Alert severity="error"` (error), then
  `data?.cars.map(...)` into MUI `Card`/`CardContent`/`Typography`; imports via the `@/` alias.
  This is the canonical shape every generated component must follow — the agent's strongest
  few-shot exemplar.
- `src/__tests__/Example.test.tsx` — **MockedProvider test pattern** (HIGH). Wraps the unit in
  `<MockedProvider mocks={[{ request: { query: GET_CARS }, result: { data: { cars } } }]}>`,
  adds `__typename: "Car" as const` to fixtures (required or Apollo cache misses), asserts with
  `await screen.findByText(...)` for async and `getByRole("progressbar")` for loading. Defines
  what a "test" means for validation.
- `src/graphql/queries.ts` — **query/mutation contract** (HIGH). `GET_CARS`, `GET_CAR($id)`,
  `ADD_CAR($make,$model,$year,$color)` already exist and select all 8 `Car` fields including
  the three image URLs. Generated code must **import** these, never redefine them.
- `src/mocks/handlers.ts` + `src/mocks/data.ts` — **MSW in-memory GraphQL handlers** (HIGH).
  `graphql.query("GetCars")`, `graphql.query("GetCar")`, `graphql.mutation("AddCar")` over a
  mutable module-level `cars` array with auto-incrementing `nextId`, generating
  `placehold.co` URLs per breakpoint. Confirms there is **no server to build** — a failure
  mode the plan must explicitly guard against.
- `src/test-setup.ts`, `vitest.config.ts`, `tsconfig.json` — **harness contracts** (HIGH).
  jsdom environment, `globals: true`, `@ -> src` alias in both Vite and Vitest;
  `strict: true` plus `noUnusedLocals`, `noUnusedParameters`, `noUncheckedIndexedAccess`.
  These four flags are the most common cause of LLM-generated TS failing `typecheck` and must
  be named in the generator prompt.

**Prior art outside the repo (evaluated, not adopted):** the `pi` coding-agent SDK
(`docs/sdk.md`, `examples/sdk/01-minimal.ts` -> `12-full-control.ts`) shows a production
shape for exactly the runtime we must write: `createAgentSession()`, an event stream
(`session.subscribe`) with `message_update` / text deltas, declarative tool allow-lists
(`tools: ["read","bash"]`, `noTools: "builtin"`, `excludeTools`), `SessionManager.inMemory()`,
and compaction for token budgeting. Useful as a **design reference to cite and borrow shape
from**; rejected as a **dependency** (see Design -> Alternative Approaches).

## Technical Constraints

**Imposed by the boilerplate (non-negotiable):**

1. Generate **into a copy of the existing project structure**, never scaffold from scratch
   (`README.md`: "Your agent should generate code into this existing project structure").
2. Output must satisfy `npm run typecheck` under `strict` + `noUnusedLocals` +
   `noUnusedParameters` + `noUncheckedIndexedAccess`. Indexed access on arrays (a very common
   LLM output) fails without a guard — must be in the prompt and in the repair loop's error
   parsing.
3. Must import `GET_CARS` / `GET_CAR` / `ADD_CAR` from `@/graphql/queries` and the `Car` type
   from `@/types`; must not redefine queries, handlers, or the seed data.
4. Must use the `@/` path alias (configured in **both** `tsconfig.json` and
   `vitest.config.ts`) — a relative-import slip breaks the test run but not the dev server.
5. Tests run in jsdom with MSW + `MockedProvider`; fixtures need `__typename: "Car"`.
6. Responsive image selection is a **hard functional requirement** at the 640px / 1024px
   boundaries, and must be testable (jsdom needs a controllable `matchMedia`/viewport stub —
   see Learning Gaps).
7. `index.html` + `public/mockServiceWorker.js` boot path (`src/main.tsx`) is already wired;
   generated `App.tsx` must remain the single composition root.

**Imposed by the submission rubric:**

8. Final output must run via `cd generated-app && npm install && npm run dev`.
9. `.env.example` must list required API keys; evaluators supply their own. Keys must never
   be committed, defaulted, or hardcoded.
10. Must survive a **slightly modified spec** — so the agent may not hardcode the Car
    Inventory feature list; decomposition must be driven by the spec text.
11. Evidence of a real loop (not a single prompt) and >= 1 retry on failure.
12. 4-6 hour budget -> the design must be right-sized: a handful of small modules, not an
    agent framework.

**Chosen by the user at the Orchestrator:**

13. Provider-agnostic LLM adapter (Anthropic + OpenAI backends, env-selected).
14. Plain TypeScript function-calling loop; no LangChain/LangGraph/CrewAI/Mastra, and
    `@earendil-works/pi-coding-agent` is **not** added as a project dependency.

## Findings Summary

Four HIGH-confidence local patterns (`Example.tsx`, `Example.test.tsx`, `queries.ts`,
`handlers.ts`) plus three harness contracts (`tsconfig.json`, `vitest.config.ts`,
`test-setup.ts`) fully specify what the agent must **emit**, so no external research is
required for the app surface; the pi SDK docs were read as prior art for the runtime shape.
Risk is **HIGH** because the task combines API integration (two LLM providers over HTTP) with
complex logic (decomposition, dependency ordering, context budgeting, retry orchestration),
and because the repo contains **zero** precedent for an agent loop, a CLI entry point, or an
LLM call — that half of the work is net-new. The binding technical constraint is therefore
not the GraphQL layer but the **typecheck gate**: the four strict compiler flags and the dual
`@/` alias config are the most likely causes of generated code failing validation, which makes
the error-parsing/repair loop the highest-risk unit to design.
