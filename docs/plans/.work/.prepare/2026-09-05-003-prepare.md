## Design Constraints Carried Into Execute

1. **The four strict flags are not hardcoded.** `tsc` reads the output directory's own
   `tsconfig.json`; the parsers only report what it emits. Measured codes (probe, 01:22Z):
   `TS6133` for `noUnusedLocals` **and** `noUnusedParameters`,
   `TS2322` (`Type 'string | undefined' is not assignable to type 'string'`) for
   `arr[i]` under `noUncheckedIndexedAccess`. Diagnostic line format:
   `src/bad.ts(2,9): error TS6133: <message>` with indented continuation lines and an npm
   `> <pkg>@<ver> <script>` banner to ignore.
2. **Machine-readable flags must be appended outside the allow-list check.** `run_command`
   normalizes to a bare script name and rejects anything with arguments, so `--pretty false` /
   `--reporter=json` cannot be expressed as a model command. `validate.ts` therefore runs the
   allow-listed script names (`typecheck`, `test`) through `executeTool`, and supplies the
   `ScriptRunner` seam that maps those script names to `npm run <script> -- <flag…>`. Allow-list
   enforcement stays with T05: a non-allow-listed script surfaces as `command_not_allowed`.
3. **vitest JSON facts (probe, 01:23Z).** `npm run test -- --reporter=json` prints the npm banner
   then one JSON object on **stdout**: keys `numTotalTests`, `numFailedTests`, `success`,
   `testResults[]`; per-suite `name` is an **absolute** path (must be normalized to
   output-dir-relative), `status`, `message` (suite-level failures), and
   `assertionResults[]` with `fullName`, `status`, `title`, `ancestorTitles`,
   `failureMessages[]` whose first line is `AssertionError: expected …` and later `at <file>:<line>:<col>`
   frames give the assertion line.
4. **Failure-to-false-green is the risk to design against.** Unparseable `test` output and a run
   with zero collected tests must surface as errors, not as `ok: true`; a missing `node_modules`
   must return an actionable message, not a stack trace.
